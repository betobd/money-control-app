# ADR 0008: Configurable base currency and full ISO-4217 support

- Status: Accepted
- Date: 2026-08-26
- Supersedes the currency scope of [ADR 0005](0005-multi-currency-cop-usd.md);
  its money representation, snapshot model and transfer model are unchanged.

## Context

ADR 0005 fixed the base currency to COP and the supported set to `{COP, USD}`.
Both were right for a personal build. Neither survives publication: a user in
Mexico needs MXN totals, not "estimated in COP", and a user holding EUR needs a
EUR account.

Two things made this more than a widened enum.

**`BASE_CURRENCY` was decoration.** It was exported from the registry and
referenced in exactly one place: its own definition. The actual base-currency
decision was spelled out as **29 `currency === 'COP'` comparisons across 37
files**, each meaning "is this the base currency?" and each wrong the moment the
base is not COP — a user's own accounts would be labelled foreign and excluded
from their own net worth.

**Stored data did not describe itself.** `base_amount_minor` meant "COP" and
`exchange_rate_scaled` meant "COP per USD" because nothing else was possible. A
transfer between two non-base currencies, now representable, has no such
convention to fall back on.

## Decision

### Supported currencies

- The registry holds the **160 spendable currencies** Frankfurter quotes,
  generated by `scripts/generate-currency-registry.mjs` from its
  `/v2/currencies` list plus ICU minor-unit data.
- Metals (`XAU`, `XAG`, `XPT`, `XPD`) and `XDR` are excluded: they are priced per
  troy ounce or are a unit of account, and neither has minor units, so neither
  fits the integer-minor-unit money model.
- `fractionDigits` is **frozen once shipped**. It defines what a stored integer
  *means*: changing a currency from 0 to 2 digits silently divides every existing
  amount by 100. `tests/currency.test.mjs` pins the values in use.
- **COP is deliberately `fractionDigits: 0`** — whole pesos — even though ISO 4217
  and ICU say 2. Existing rows are whole pesos, and generating this field from ICU
  would have reinterpreted every stored COP amount as centavos.

### Base currency

- Stored in a new `app_settings` singleton row, not a constant.
- **Changeable freely until the install has something denominated in it**, and
  fixed afterwards. "Something" is a transaction or a budget:
  `SettingsService.baseCurrencyLock` reports which, and the UI shows the reason
  rather than a disabled button with no explanation.
- The reason it is fixed is not caution. Every transaction stores a
  `base_amount_minor` snapshot and every budget limit is an amount, both in the
  old base. Restating them honestly needs the exchange rate *on each original
  date*, which this app deliberately does not keep (ADR 0005, Option A).
  Converting them at today's rate instead would rewrite closed months — which is
  the behaviour that makes other apps' historical reports drift.
- Read through a process-wide cache primed during database initialization
  (`DatabaseGate` renders nothing until it completes), so screens can ask
  synchronously during render. Reading before the cache is primed **throws**: a
  guessed base currency does not fail loudly, it silently writes wrong snapshots.
  Services take it as an injected function, because `tsx` can load one module
  under two specifiers and a process-global would not be deterministic in tests.

### Self-describing snapshots

`transactions` gains three columns:

- `base_currency_code` — which currency `base_amount_minor` is in. NULL for
  transfers, which carry no snapshot.
- `exchange_rate_base_code` / `exchange_rate_quote_code` — the pair
  `exchange_rate_scaled` describes, read as **1 base = rate quote**.

The old rule "a foreign row must carry a rate snapshot" was written
`currency = 'COP'`. A CHECK cannot read a settings table, so it is now stated
against the row's own `base_currency_code` — strictly as strong, and readable
without knowing the current setting.

Backfill is exact, not inferred: every pre-0014 non-transfer row was COP-based,
and every rate snapshot that could exist was written as "1 USD = r COP".

### Database validates shape, not membership

The closed `IN ('COP','USD')` CHECK on six tables becomes
`GLOB '[A-Z][A-Z][A-Z]'`. Enumerating currencies in the schema would mean a
destructive migration every time one is added; the allowed set lives in the
TypeScript registry and is enforced by the repositories. The database still
rejects `eur`, `EU`, `EURO` and `US$`.

> A CHECK rejects only a FALSE result, never a NULL one, and `NULL GLOB '…'` is
> NULL. Every such constraint puts its `IS NOT NULL` guards first. The first draft
> of `transactions_rate_pair_valid` did not, and accepted exactly what it existed
> to reject.

### Exchange rates: star topology

- One rate per foreign currency, always against the base, keyed
  `${foreign}-${base}` — the orientation a user recognises ("one dollar is 4,102
  pesos") and the one every existing row already used.
- Fetched per currency (`/v2/rate/{base}/{quote}`), concurrently. A user holds a
  handful of currencies; a single call per currency keeps each rate at full
  precision, which a shared-base call does not.
- **`rateScale` is chosen per rate.** No fixed scale serves every pair: at four
  decimals `1 COP = 0.00024 USD` keeps two significant digits. The scale rises
  only until the value carries five, so a rate is never padded with zeros the
  provider did not send.
- `deriveEffectiveRate` states a transfer's rate in whichever direction gives a
  value ≥ 1, for the same reason. The pair travels with the rate, so both
  directions are equally usable and one is far more precise.
- A currency with no rate is **excluded and named**: net worth reports
  "Estimated — incomplete" and says which currencies are missing, so the warning
  is actionable. It is never counted as zero.

### Backup format v7

- `currency` names the base currency the file was written with, instead of the
  literal `'COP'` every earlier format assumed.
- `data.exchangeRate` (one pair) becomes `data.exchangeRates` (one row per pair);
  `data.baseCurrencyCode` records the base.
- Restoring **adopts the backup's base currency**: its stored
  `base_amount_minor` values make sense in no other.
- v1–v6 upgrade by labelling, never converting: base `'COP'`, rate pair
  `USD`/`COP`. Numbers are untouched.

### CSV export

Column names keep their `_cop` suffixes (`amount_cop`, `limit_amount_cop`,
`estimated_base_currency_balance_cop`). They now hold the base currency, which
`currency_code` and the export metadata name. Renaming them would break every
spreadsheet built against an earlier export for no gain in meaning; they are
frozen as historical names.

## Migration

`0014_configurable_base_currency` rebuilds nine tables with the create-copy-swap
pattern of 0008/0009/0012, because SQLite cannot alter a CHECK. Every `CREATE` in
it is the **exact DDL SQLite reported for the table it replaces**, generated
rather than transcribed, with only the currency constraint rewritten — a
hand-copied rebuild of that size is how a column, index or trigger goes missing.

`app_settings` is seeded from the data: an install that already has accounts was
COP and stays COP; an empty one gets a neutral default the user can change freely.

`tests/configurable_base_currency_migration_database_test.py` asserts that every
row, index and trigger survives, that the backfill is correct, that new currencies
are accepted and malformed ones still rejected, and that the rebuilt triggers
still fire.

## Consequences

- Accounts, transactions, recurring rules, investments and budgets work in any
  supported currency; consolidated totals follow the user's chosen base.
- Currency pickers are searchable; 160 chips in a row were not an option.
- Adding a currency is a registry regeneration, not a migration.
- Out of scope: changing the base currency after history exists, historical daily
  FX valuation, FX gain/loss, and per-currency number formatting (display grouping
  follows the registry, which uses the dot-decimal convention the money parser
  accepts so what is shown matches what is typed).
